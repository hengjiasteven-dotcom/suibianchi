# 随便吃 · 技术方案 v0.1

前置文档：需求规格 v0.2
状态：与需求文档配套，尚未开始编码
更新日期：2026-10-07

## 1. 总体架构

```
Android 客户端 (Kotlin + Jetpack Compose)
        │  HTTPS / JSON
        ▼
自有服务器 (Python FastAPI + PostgreSQL)
        │
        ├── DeepSeek deepseek-flash  → 图片识别、对话、推荐生成
        ├── 七牛云对象存储            → 餐食原图（私有空间 + 签名访问）
        ├── 短信服务商                → 注册/登录/找回密码
        ├── 地图开放平台              → 按需检索附近商家（不建库）
        └── 本地热量索引              → 1202 条，随服务端部署，不调用 AI
```

关键分工：

- 热量数值来自本地热量索引，AI 不负责算热量，避免模型随口报数。
- AI 负责三件事：看懂图片、抽取结构化信息、生成推荐与建议。
- 商家信息按需实时检索，用后即弃，不建全量库。

## 2. 数据模型

### 2.1 账号与档案

- `users`：手机号、密码哈希（Argon2）、状态、创建时间
- `devices`：设备令牌哈希、最近登录时间，用于免验证码快速登录
- `user_profiles`：城市、膳食目标（多选）、更新时间
- `food_restrictions`：忌口 / 过敏 / 规避项，来源（手动 / 对话抽取）、是否已确认
- `taste_preferences`：口味爱好，带权重

说明：忌口是硬约束，写库前必须经过用户确认；爱好是软约束，可直接写入。

### 2.2 餐食记录

- `meal_records`：用餐日期（meal_date）、餐次（早/午/晚/夜宵）、用餐时间、来源（下厨 / 外卖，由识别判断，用户不用选）、备注、状态（估算中 / 已确认）；同一用户 + 日期 + 餐次唯一，重复提交按覆盖处理
- `meal_photos`：七牛云 key，不存图片本体
- `meal_items`：识别后的每个食材，含原始名称、匹配到的热量索引编码、热量、烹饪方式、匹配状态

规则：记录无删除入口，仅可编辑；支持最多回溯 2 天补录；未记录的餐次留空，不计入统计分母。

### 2.3 对话

对话原文**不落库**，只保留结构化结果：

- 进行中的会话放在 Redis，设置 10 分钟 TTL，用户离开 App 超过 10 分钟自动结束并清空
- 抽取出的忌口 / 爱好写入 `food_restrictions` / `taste_preferences`
- 忌口类写入前必须弹确认

### 2.4 热量索引

热量不再依赖本地食物索引，改为 AI 逐食材估算：

- AI 对每种食材输出：名称、份量描述、克数、每百克热量、这一份热量
- 服务端用「克数 × 每百克热量 ÷ 100」重算每条热量，与模型自报值偏差超过 25% 时以重算值为准
- 餐次合计由服务端累加各食材，不采用模型自报的总量，保证明细与合计一致
- 界面统一标注“约 XXX kcal（估算）”，不做每日目标与达标提醒

本地保留的 1211 条食物数据仅作为可选参考（`SHIJI_AI_INCLUDE_INDEX=1` 时拼进提示词），不在主流程上。

### 2.5 统计与分享

统计不落表，按时间窗口实时聚合（数据量小，够用）。分享卡片需要留痕时写入 `share_cards`，记录类型、内容快照、过期时间。

## 4. Android 页面结构

1. 启动与登录：启动页 → 手机号 → 验证码 → 首次设置密码
2. 记录页：聊天窗口式的发布流，一条左一条右（什么时间 + 哪一餐 + 菜品 + 材料 + 总能量 + 备注），底部通栏「发布这一餐」按钮
3. 日志页：默认周视图的日历课表；双指一缩展开到月，双指一张退回周/日；点某一天看当天四餐，点某一餐看详情并编辑（最多补录回溯 2 天）
4. 外壳：背景图（只轻微降模糊，照片本身要看得清）+ 半透明毛玻璃面板；下方 TAB 栏与上方内容约 1 : 6.7
5. 记录流程：拍照 / 选图（可多张、可零张）+ 文字 → 识别中 → 只核对食材名称 → 确认即入库 → 后台估算完成后自动显示热量
6. 记录详情：查看与编辑，不提供删除；改过名的食材在保存时重新估算热量
7. 日志补录：支持补录今天 / 昨天 / 前天（最多回溯 2 天）
8. 推荐页：选择下厨 / 外卖 → 方案列表 → 外卖附附近店铺
9. 对话页：纯文字，进入前提示“退出将清空对话”
10. 报告页：3 天 / 周 / 月 / 季度，环形图 + 结论 + 缺口提醒
11. 分享页：当日用餐（文字）/ 最近一周（图表），均不含照片与隐私
12. 广场：以后用来分享每日一餐与饮食报告（当前为空状态占位）
13. 个人主页：右上角头像进入，含头像 / 名字 / 用户 ID / 个性签名 + 资料（城市、性别）+ 权限 + 账号（退出登录）；不放吃饭相关的内容（膳食目标、忌口属于以后的饮食报告）

## 5. 关键流程

### 记录一餐

1. 客户端上传图片到七牛云（服务端签发凭证）
2. 客户端调 /recognition，服务端取图后调 DeepSeek 得到结构化结果
3. 客户端展示可编辑的食材/菜品名称（不显示热量），用户增删改
4. 用户确认名称 → 写 meal_items 并入库，meals.status = estimating，接口立即返回
5. 服务端后台任务调 DeepSeek 逐项估算热量，回填 meal_items 并把 status 改回 confirmed
6. 客户端轮询 /meals：没算完就显示“热量估算中…”，算完自动换成实际值
7. 入库后仍可编辑：改过名的食材保存后会重新走一遍后台估算；估算失败用本地索引兜底

### 生成推荐

1. 校验硬约束（忌口 / 过敏）
2. 汇总近期摄入缺口
3. 组装提示词：膳食目标 + 缺口 + 爱好 + 场景 + 时间成本
4. DeepSeek 产出 3-5 套方案；外卖场景再按需检索附近店铺
5. 结果附热量参考值，标注“估算”

### 对话式推荐

1. 进入对话页，提示退出即清空
2. 用户描述当下想吃什么
3. 服务端带着最近用餐记录与档案生成回复
4. 若识别到忌口，弹确认框；确认后才写入档案
5. 满意退出 → 清除 Redis 会话

## 6. 风险与待确认

1. 《中国食物成分表》数据授权：目前是自建索引用于估算，若要对外宣传数据来源需先确认授权。
2. 地图服务条款：附近商家检索需遵守配额与署名要求。
3. 图片隐私：原图存七牛云私有空间，需在隐私政策写明保存期限与删除方式。
4. 热量估算口径：只展示参考值，不做每日目标与达标提醒。
5. 少量转置排版页未提取（如第一册第 116 页），后续按需增量补录即可。
